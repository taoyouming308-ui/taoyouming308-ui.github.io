# Private media runtime preparation: actual local decode, durable synthetic storage, cloud protocol mocks

All factories are disabled by default. This stage does **not** enable real photo uploads, provision credentials, change production RLS, deploy a worker, or call Supabase/AI over the network. It does not install dependencies. It adds three independent pieces; they must not be described as one completed production storage service.

## 1. Native full image decoder

`createNativePrivateImageInspector({enabled,magickPath,pythonPath,expectedVersion,syntheticOnly,workerTimeoutMs})` returns the `imageInspector(bytes)` callback for `private-media.mjs`.

It is a **Node + native subprocess** implementation, not compatible with the existing Supabase Edge runtime. The currently reviewed/tested installed executable is ImageMagick **7.1.2-17**, Q16-HDRI on this macOS host. Paths are explicitly provided, resolved to real files and never searched through an untrusted PATH. No software is downloaded. Every request probes the actual version and effective policy again; there is no stale version cache. Different releases fail closed until separately reviewed. Deployment must make the binary, Python launcher, configuration and dependency files immutable to the worker identity; a version probe is not a signature check or protection against a privileged executable swap between subprocesses.

The implementation:

- Copies at most 8 MiB of input, validates complete JPEG/PNG/WebP container boundaries, rejects trailing concatenated payloads, WebP/PNG animation markers and JPEG multipicture containers. It does not claim to eliminate every possible embedded metadata/polyglot ambiguity.
- Forces the already-determined JPEG, PNG or WEBP coder. It performs **full decode and decoded-pixel signature calculation** with `%#`, not `identify -ping` or header inspection. `-regard-warnings` turns decoder warnings into failures. A correct PNG container/CRC with corrupted compressed pixel data is rejected by the actual native decoder in tests.
- Uses a private mode-0700 temporary directory and mode-0600 original file. The original filename is never supplied. Shell interpolation is never used; input-derived text is never a command or format expression. Temporary originals/config are removed after success/failure/timeout. An abrupt parent-machine/process crash can leave private temporary files; production needs an ephemeral worker filesystem and an approved crash-cleanup policy.
- Probes effective ImageMagick policy, requiring only JPEG/PNG/WebP read coders and INFO output; all delegates and dynamic filters are denied, indirect `@` paths are denied, no pixel disk/map cache is allowed. Arbitrary client paths/URLs are not accepted. Output is a bounded format/dimension/frame-count/signature line; no EXIF/comment/filename dump is returned. The signature is not in the public result.
- Applies 256 MiB ImageMagick pixel-cache memory, no map/disk spill, 16384 maximum side, 40 MP post-decode ceiling, one accepted frame, and one thread. ImageMagick's working list limit is two because its internal single-image pipeline needs that slot; input animation rejection plus the final frame count still require exactly one frame.
- Starts a standard-library Python launcher that requires a 768 MiB address-space limit, 3 CPU-second hard limit, zero core/file-output limit and 64 descriptors. The default overall request wall budget is 5 seconds across version/policy/decode subprocesses, with bounded stdout/stderr. Timeout kills the child; diagnostics are redacted.
- Allows only one active request **per inspector instance**, immediately rejecting other calls with `IMAGE_WORKER_BUSY` before copying/queuing their image bytes. Timeout and all errors release admission. A caller can create other instances; deployment still needs process/worker-wide concurrency, upload admission, memory budgets and rate limits. This factory is not a global service scheduler.

### What was actually verified about memory/isolation

On this macOS host, setting `RLIMIT_AS`/`RLIMIT_DATA` is unsupported: Python raises `ValueError`. Default strict mode therefore refuses with `IMAGE_HARD_MEMORY_LIMIT_UNAVAILABLE`. The local acceptance suite explicitly uses `syntheticOnly:true`, which permits **only on macOS** the absence of that hard address-space limit. CPU, wall time, pixel-cache/pixel/frame/FD/file limits remain in place. The flag does not inspect or prove that a picture is synthetic; test authors ensure that input consists only of locally generated colored pixels. It must never be enabled for real uploads. The positive full-decode tests on macOS are **not** evidence of a production hard-memory sandbox.

ImageMagick policy and resource limits are defense in depth, **not OS network/filesystem isolation**. A native decoder vulnerability could bypass application policy. Production remains blocked until an approved controlled worker/container supplies a restricted identity, no network egress, narrowly mounted ephemeral input/output filesystem, immutable reviewed binaries, OS memory/CPU/process limits and global admission control. A successful RLIMIT_AS call alone does not establish those guarantees. This stage has not run or certified that Linux/container deployment.

The return value is exactly `{mime,width,height,frameCount:1,decoded:true}`. No transcoding occurs. JPEG EXIF/other metadata remains in the privately stored original; a tested EXIF-bearing synthetic JPEG survives byte-for-byte. An external sanitized derivative requires a separate consent, provenance and implementation decision. No photo is sent to any model.

## 2. Durable local fixture, not a cloud bucket

`openSyntheticDurableMediaRepository({enabled,optIn,directory,allowedBindings,fixtureSha256,fault})` implements the existing `private-media.mjs` repository interface using a private single-file manifest containing **both original bytes and metadata**. `optIn` must equal `MEDIA_FIXTURE_OPT_IN` and NODE_ENV must not be production. It only opens an explicit directory below a dedicated `design-media-fixture-*` system-temporary parent. Allowed owner/store strings must be synthetic; exact scope bindings and the SHA-256 values of all permitted fixture images are declared in advance. This whitelist is a test configuration, not an automatic detector of real versus synthetic photos.

- One exclusive on-disk writer lease per directory, serialized scope operations, no automatic stale-lock takeover, immutable media IDs, no upsert/delete API. Closed transaction handles cannot be reused.
- Stages a complete bounded manifest, writes/fsyncs it, awaits the final media authorization/approval hook, atomically renames it, then fsyncs its directory. Bytes and reference metadata become visible together. A post-publication error is treated as uncertain, and identical request replay verifies the original record and bytes instead of duplicating it.
- A persisted initialization marker prevents a missing previously initialized manifest from silently becoming an empty store. A partial initialization, corrupt manifest, checksum mismatch, unexpected files, symlink, scope mismatch or changed content fails closed. Normal close/reopen restores data.
- Owner-only files/directories; maximum 16 objects and 24 MiB serialized manifest; original per-object limit remains 8 MiB. Checksums detect accidental corruption, not a privileged malicious administrator who can replace the directory and its entire history. Retention, backups and automatic repair are not implemented.

The transaction/approval mock in these tests is not a real employee database lock. The file rename proves local single-file publication behavior; it does **not** prove cross-system authorization atomicity, Supabase transaction correctness, power-loss recovery under every filesystem, or production cloud durability.

## 3. Prepared existing private Supabase Storage protocol and publication bridge

`createPreparedPrivatePhotoStorage({enabled,origin,transport,authorize})` prepares actual request descriptors using the same existing `/storage/v1/object/customer-design-photos/...` upload/read routes as the tracked production photo module. It accepts only a configured HTTPS `*.supabase.co` origin with no userinfo/path/query, never a client-supplied destination. It provides `stage({record,bytes})` and `read({record})`; there is no fetch fallback, signing endpoint, public URL or credential parameter.

- A canonical full employee/store/profile/visit/source binding determines an internal prepared object path. Caller/dependency mutation and JSON property ordering cannot redirect it. Records, binding and authorization intents are deeply frozen copies. The physical path is not returned to the client.
- POST uses `Content-Type` and `x-upsert:false`; GET readback verifies exact original byte length and SHA-256. Redirects, mismatched destinations and corrupt bytes are rejected. The injected **trusted server transport** is responsible for attaching its already-authorized server credentials internally, enforcing the supplied 10-second timeout and response-byte cap before buffering, refusing redirects, and suppressing sensitive logs. These network/credential capabilities are not configured or exercised here.
- Unknown POST outcomes and an immutable conflict are followed by at most one authorized **read-only** reconciliation, never an automatic second POST, upsert or DELETE. A matching object can proceed to metadata publication. Missing/mismatched/denied readback remains `PRIVATE_STORAGE_OUTCOME_UNCERTAIN`, `retryable:false`. Withdrawal after a POST may have left a staged object and is also uncertain. Authorization denial before the POST performs no request.
- `authorize` must check the authoritative employee/scope and operation-specific approved destination in its server request/transaction context; a binding object is not a credential. Origin in the actual storage adapter, `approvalRecipientOrigin` in the bridge and `privateStorageOrigin` in the outer media adapter **must be identical** and independently tied to the exact approval. Do not build this callback from client claims.

`createPreparedPrivateMediaPublicationRepository({enabled,objectStorage,metadataRepository,approvalRecipientOrigin})` composes storage with an injected authoritative metadata transaction:

1. The outer private-media module checks employee/scope, full decode and exact upload approval.
2. Stage original bytes at an immutable private object locator and verify readback.
3. Insert metadata with `metadataRepository.withScopeLock` and its `readRecord`, `insertImmutable(record)`, `beforeCommit(check)` interface. The metadata transaction must implement real binding locks, CAS/unique constraints, rollback and final approval/authorization recheck through commit. It returns the original callback result after commit.
4. Reads from the publication repository require a committed metadata record. Unpublished staged objects are not returned through this path.

**This is intentionally not a distributed atomic transaction.** A failed metadata commit may leave a private orphan object. It is neither exposed nor auto-deleted; a later explicitly authorized identical request can reconcile it and publish once. Lost metadata acknowledgements are reconciled using the committed record. Cloud orphan cleanup, expiry, restricted storage service privileges, read/RLS rules and credential provisioning require a separate reviewed operational design. No new production policy is installed here, and the safety of an existing live bucket is not inferred from these mocks. The prepared `prepared/` object prefix is not a claim that legacy asset rows or UI automatically adopt these records.

## Independent acceptance commands

- `node scripts/test-design-private-media-native.mjs`: actual installed native decoder on locally generated PNG/JPEG/WebP and EXIF-bearing colored-pixel fixtures, plus isolated durable files/restarts/corruption/fault injection. Uses macOS synthetic-only memory fallback explicitly; strict-mode refusal is tested. Override `DESIGN_MEDIA_MAGICK`/`DESIGN_MEDIA_PYTHON` with reviewed absolute paths when needed; the exact reviewed ImageMagick version is still required.
- `node scripts/test-design-private-media-storage.mjs`: prepared official route, immutable staging/readback, binding freezing/canonical paths, authorization/redirect/lost-ack and metadata-publication behavior using mock transport and in-memory metadata only. `fetch` is forbidden; no real request occurs.

Current production blockers: controlled isolated native worker and hard-memory validation; real credential-bearing bounded storage transport authorization; authoritative metadata transaction and permissions; cleanup/retention policy; separately approved deployment and real integration acceptance. No listener, real key, real photo, paid operation or model-image format is introduced.

Protocol/policy references checked during review: [ImageMagick security policy](https://imagemagick.org/security-policy/) and [Supabase standard uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads). Standard immutable upload is not resumable upload; files over 6 MB have a reliability recommendation for resumable transfer. The current 8 MiB prepared limit preserves the existing App limit, while uncertain outcomes require readback rather than blind re-upload. No resumable upload implementation or live reliability test is claimed.

The installed `7.1.2-17` pin identifies the version exercised by these fixtures, not a production security certification or “latest” claim. The vendor page inspected during this review lists `7.1.2-35`; production activation must review security updates, choose a maintained build and rerun policy/decode/isolation acceptance on that exact build. No local software upgrade was performed.
