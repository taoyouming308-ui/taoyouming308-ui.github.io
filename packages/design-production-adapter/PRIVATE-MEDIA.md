# Private media preparation, disabled

This is offline preparation, not a deployed media endpoint. `private-media.mjs` defaults to disabled, has no storage SDK/client or credential lookup, performs no default network calls, signs no URL, generates no credential, and does not change production RLS. Tests use fake image headers, a synthetic decoder and in-memory transaction mocks. No real image, upload, employee session or model call is used.

## Existing boundary inspected

The existing `supabase/functions/_shared/customer-design-archive.ts` uses the private `customer-design-photos` bucket, validates JPEG/PNG/WebP magic and an 8 MiB byte limit, preserves original bytes, deduplicates by request ID/content and rejects cross-visit archive references. Its `photoURLs` operation creates five-minute signed URLs. The bucket migration declares it private. No existing handler, policy, bucket or URL flow is changed by this module.

The new prepared flow is intentionally stricter: media belongs to the exact authenticated employee owner, store, customer profile, visit and assignment source. It has no all-store/owner-global fallback. Existing legacy assets cannot be silently adopted: they need a separately reviewed owner/binding migration. Reassignment does not automatically expose the former employee's assets; a new policy and explicit transfer decision would be required.

## Dependency contract

`createPreparedPrivateMedia({enabled:false,permissionGate,approvalVerifier,imageInspector,repository,privateStorageOrigin})` requires every dependency before any operation can run. `privateStorageOrigin` is a fixed trusted HTTPS origin, not a browser-selected bucket/URL.

- `permissionGate.authorize(credential,scope)` must implement the existing authoritative employee/session/assignment/customer gate and return an exact grant. Credentials are opaque and never persisted, returned or sent to storage. Scope is validated with `validateProductionDesignScope`.
- `approvalVerifier.verify(receipt,intent,phase)` must verify the actual user's authorized purpose, data and recipient. It must not trust browser booleans. Upload intent binds employee/store/profile/visit/source, requestId, original-byte SHA-256, actual size/type, stage/angle and exact private storage recipient. Read intent binds the exact asset/hash and recipient employee. Reference intent is separately bound to archive use and exact ordered IDs/hashes. Before-return/before-commit rechecks must honor withdrawal. An approval to privately upload/view/archive does not authorize sending a photo to a model or others. Signature, expiration and receipt issuer validation belong to this trusted integration. Multiple verification phases for one operation do not themselves authorize duplicate writes or broader use.
- `imageInspector(bytes)` is a mandatory trusted **full image decoder**, returning exactly `{mime,width,height,frameCount,decoded:true}`. It must fail on malformed/truncated/polyglot files, unsupported formats, animations, decompression bombs, parser errors or resource exhaustion. It must apply bounded CPU/time/memory decoding, and must not upload, transform or log originals. The built-in magic check is only an early filter, not proof of a decodable image. Supported scope is single-frame JPEG/PNG/WebP, up to 8 MiB, dimensions at most 16384 per side and 40 million pixels total. No decoder package is installed or implicitly enabled here.
- `repository.withScopeLock(binding, callback)` is a trusted **private publication transaction**, scoped by `{owner,store,scope}`. It must invoke the callback exactly once and return its result unchanged only after a successful commit. The callback receives `readRecord(mediaId)`, `readBytes(mediaId)`, `insertImmutable({record,bytes})`, and `beforeCommit(check)`.
  - `readRecord` returns null or the exact immutable record schema in this module. `readBytes` is server-only and never returns URLs; reads must themselves be bounded before buffering, not just checked afterward. The authenticated storage adapter must not use redirects or arbitrary object URLs. Never log private bytes/paths.
  - `insertImmutable` stages the original exact bytes and metadata under the full binding and returns true only for an unoccupied media ID. No upsert/overwrite is allowed. Same requestId + same complete content is replayed; changed payload or binding conflicts. IDs are references, never bearer capabilities. Physical object naming remains internal to the repository and must not use names supplied by the browser.
  - `beforeCommit(check)` must await the registered authorization/approval check immediately before atomic publication, with relevant identity/assignment/consent locks or equivalent authoritative guarantees held through commit. Throwing rolls back publication. Object storage and DB cannot be assumed atomic: a real implementation needs private staging plus transactional publication, and a reviewed orphan cleanup/retention policy. If it cannot provide this, leave the adapter disabled. A process-local mutex and sequential REST calls do not satisfy the contract.
  - A `MEDIA_OUTCOME_UNCERTAIN` failure means a write may have committed. Never automatically issue a new request ID or delete an object. Retain the exact request and reconcile through authorized readback; an explicitly requested same-ID retry verifies immutable metadata and bytes. These tests simulate commit-response loss, not a real database transaction.

## Public adapter operations

- `upload({credential,scope,approval,requestId,bytes,mime,stage,angle})` accepts only exact fields, snapshots supplied bytes, verifies type/actual size/decoder, approves exact storage transmission, stages immutable originals, then checks commit and authorization. Stages: `before | after | reference`; angles: `front | back | left | right | detail`. No filename, caption, URL, provider, owner override, EXIF-derived identity or image description is accepted. It returns `{reference,replayed}`.
- `read({credential,scope,approval,mediaId})` verifies exact ownership/scope, approval, immutable-byte hash, actual decode and dimensions, then checks authorization/metadata/approval again before returning `{reference,bytes,cacheControl:'private, no-store',maxAgeSeconds:0}`. A future HTTP wrapper must enforce these headers and `X-Content-Type-Options: nosniff`, suppress logs/caches, and expose it only to the verified employee. This is a per-request authenticated proxy-style preparation, not a signed URL or access token. There is no reusable bearer capability or URL TTL to revoke.
- `resolveReferences({credential,scope,approval,mediaIds})` permits at most 30 unique references and returns only `{references}` after exact current scope checks and separate archive-purpose approval. It is **not** a lasting authorization grant: the archive transaction must re-resolve/check these references at commit; never accept an earlier returned list as proof of current access. It neither writes an archive nor copies an asset into another visit.

A reference contains only `mediaId,stage,angle,mime,byteLength,width,height`. Storage paths, hashes, owner identity, filenames, approval receipts, credentials and private URLs never appear in successful public metadata. Errors are stable redacted codes and never carry dependency diagnostics; all failures set `retryable:false`.

## Privacy and remaining integration boundaries

Original bytes are preserved without recompression, matching the existing archive requirement. Therefore embedded EXIF/GPS or other original metadata remains inside the private original. An approval and authorized viewer must understand that originals can contain that information. This module neither strips metadata nor claims anonymization; any sanitized derivative needs separately defined provenance and cannot silently replace the original. No real photo is read in tests.

Revocation checks prevent a late request from returning bytes after the authoritative gate or approval has denied it. They cannot recall bytes already delivered or stop another system changing permissions between separate reads and a network response. Production must provide the stated transaction/session/consent coordination. An inactive record is denied; this module does not physically delete originals, cancel vendor keys or alter retention policies.

Model images remain disabled. There is no guessed provider image schema, URL sharing, photo-to-prompt conversion or image analysis route. Upload/view approval never implies model-recipient or paid-call approval. Production still needs a trusted decoder implementation, scoped private storage transaction, actual consent receipts, HTTP upload/response bounds, a secure employee-only UI and authorized real integration tests. No PostgreSQL/storage-server verification is claimed.

Run only the synthetic suite: `node scripts/test-design-private-media.mjs`.
