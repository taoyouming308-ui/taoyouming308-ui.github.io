## Storage decision: verified vendor limitation, not another mock milestone

Current official Supabase documentation explicitly lists S3 versioning and bucket
object lock as unsupported. Deleted objects are not retained as recoverable native
versions. Consequently the existing `design-private-versioned-backend-v1` cannot
be honestly supplied by ordinary Supabase object-path storage. Do not spend a live
qualification call trying to prove that unsupported native capability.

- https://supabase.com/docs/guides/storage/s3/compatibility
- https://supabase.com/docs/guides/storage/uploads/standard-uploads
- https://supabase.com/docs/guides/storage/security/access-control
- https://supabase.com/changelog.md

Recommended decision for an owner-only pilot, subject to explicit acceptance:
retain Supabase and introduce a DISTINCT application-content-addressed-manifest
contract. Unique scoped content objects plus SHA/length/MIME and append-only DB
manifest revisions may protect application references, provided the runtime has
only bounded INSERT/SELECT, never UPDATE/DELETE or a service key bypassing RLS.
Read exact manifest targets and hash bytes; never latest/path fallback. Unknown
PUT receipts must be reconciled read-only against the original durable claim, not
blindly resent. Manifest failure must not publish an unbound object. Existing
native-version contract and all old stored provenance stay unchanged.

This alternative is not WORM or native retained-version recovery: a project admin,
owner or provider can delete data. Such deletion/tampering is detected and fails
closed; it does not restore deleted bytes or guarantee availability. Owner must
accept this boundary and choose retention/deletion responsibility before adopting
it. Otherwise choose a vendor with actual retained version reads and explicit
retention controls, with a new vendor locator contract and separately approved cost.

Only after that decision: owner verifies project/region, private bucket or prefix,
usage/Spend Cap and total test budget; approve exact least-privilege service role,
secret delivery and one synthetic external qualification. No key in chat. Run a
finite suite: competing create, denied overwrite/delete/cross-scope, lost PUT ack
read-only recovery, failed manifest commit, altered bytes/mapping rejection,
revocation and historical readback. Runtime bypassRLS, mutable manifests, reused
object paths, unchecked reads or fabricated native versions are stop conditions.
No such role/resource/configuration or live test was created in this stage.
