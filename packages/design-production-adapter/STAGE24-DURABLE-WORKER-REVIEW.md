# Stage24: bounded durable worker execution

Status: isolated implementation under review, not production deployment approval.

## Scope and trust

The worker is a finite explicitly invoked pump, not a scheduled daemon. Default flags remain closed; no environment credential discovery, host provisioning, production migration, real customer data, provider billing or automatic retry is enabled. The original homepage queue/status/adoption flow remains the consumer. This synthesis worker does not satisfy the separate controlled Linux image-decoder deployment gate.

The independent worker uses an exact `design_synthesis_worker` LOGIN adapter. The original runtime adapter still accepts only `design_identity_runtime`. Physical leases and quarantine are shared to prevent the same socket being borrowed across adapters. Worker release destroys the physical connection rather than assuming job context was reset. No arbitrary role option is added.

Two additive fixed SQL capabilities return job-bound source inputs and the current approved encrypted key respectively. Each checks original session, immutable identity, current service binding, source, ancestors, approval, key and lease fence in a short transaction. Neither returns or stores an employee bearer. The local deterministic path never requests a key. No direct table privilege or approval-issuance capability is granted to the worker by this offline draft.

The trusted Node execution reconstructs the original fixed synthesis prompt and validates the complete intent, body hash, evidence and source binding. The existing strict synthesis response parser and candidate validators remain authoritative. Cryptographic key opening is outside the database transaction, tied to the immutable owner domain and approved key digest. A final durable dispatch transaction checks current authorization and consumes the original approval. Only an acknowledged successful dispatch claim permits one transport invocation, without intervening asynchronous work. A lost claim acknowledgment permits zero transport invocations by that execution.

## Interruptions and cancellation

External I/O is outside SQL transactions. A finite job deadline of at most30 seconds applies in this pump; this does not extend a session, approval, job, lease or candidate TTL. A separate at-most1-second best-effort cleanup may settle an attempt. Timeout or uncertain cleanup poisons the pump instance; subsequent use is refused rather than accumulating unresolved work. Late promises cannot resume candidate publication. A finite batch processes at most32 jobs and stops on the first non-completion.

An uncertain claim, dispatch, provider response or finish acknowledgment is never an instruction to resend. A pre-dispatch lease may only be reclaimed through the existing fenced SQL semantics. Claimed dispatch is not reclaimed for another send. Cancellation after dispatch cannot retract bytes, promise no charge, or retract an independently published/adopted artifact. Revocation may leave an original-ledger tombstone; no shortcut settles or revives it under reduced authority.

The guarantee is fresh checks at the validation/dispatch boundary, not absolute authorization at physical COMMIT or packet arrival. A compromised trusted worker cannot be cryptographically prevented from fabricating semantically valid commentary by these SQL bindings alone.

## Minimum activation package to review later

No production decision is required to finish the synthetic tests. Before any live activation, the operator must name the actual service account/host, database target and region, same-origin HTTPS routes, and the existing secret custodian. The exact runtime and independent worker LOGIN/EXECUTE changes must be reviewed against a production schema inventory; the synthetic-only SQL drafts intentionally refuse another database and are not a production migration command. The worker gets no employee/issuer role membership or general table access. Its reviewed functions, owners, search_path, PUBLIC revokes and dependency ACLs require a post-install least-privilege test and a forward rollback plan.

The personal key settings endpoint is the only eventual input surface. It must bind the verified immutable employee, use the v2 encryption domain and approved server secret provider, redact all logs, and keep credentials out of client storage, chat, task arguments and the request ledger. Synthetic fixture encryption constants must never be used in deployment. Configuration of any real key remains separate from approval to process customer data or incur a bounded model charge. Model selection and exact personal billing/data-processing approval remain explicit; an enqueue does not mint either approval.

The runtime composition exposes `runOnce`, finite `runBatch`, and `close`, not a hosted scheduler. A later operator-controlled process must stop admission, abort in-flight work and drain/close its owned driver pool on shutdown; `close` now aborts the composed pump before bounded cleanup and adapter close, but cannot retract an already dispatched request. Crash recovery must consult the same original ledger: only an eligible pre-dispatch lease may be reacquired; dispatch-claimed uncertainty must never be automatically resent. Status and reconciliation stay manual in the current UI.

Live media still requires a separately qualified isolated image decoder/storage path and explicit customer-data/recipient permission. Synthetic loopback tests do not establish TLS/CORS, operational key custody, model quality, real billing behavior or production capacity. The existing32-native/two-archive latency failure and unlocated old PG fault remain on the release checklist.
