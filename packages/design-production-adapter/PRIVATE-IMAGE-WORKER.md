# Prepared isolated image worker (stage 9)

> Stage26 clarification: these Linux requirements apply to this local-worker implementation, not every possible image-processing architecture. Existing Supabase Pro private transformations are now the preferred alternative under evaluation. See [managed-image review](STAGE26-MANAGED-IMAGE-REVIEW.md); no VM purchase or hosted activation is authorized by this document.

## Status: not deployed, not production-verified

The new driver is **off by default**. It adds a real, narrowly specified Docker launch implementation and Linux worker source, not an assertion that an approved deployment exists. This stage did not install software, build/pull/run an image, create a daemon grant, configure credentials, change a host, or send a customer image. Tests use fixed synthetic PNG bytes, mocked Docker protocol responses, and a real Python pixel encoder. They do **not** certify Linux isolation or native decoding inside the proposed image.

`createIsolatedPrivateImageWorker({enabled,dockerPath,image})` in `private-image-worker-driver.mjs` returns:

- `process(Uint8Array) -> {source,derivative}`.
- `inspect(Uint8Array) -> {mime,width,height,frameCount:1,decoded:true}` for the private-media imageInspector dependency.
- `derive({bytes,sourceSha256}) -> {bytes,mime:'image/png',sourceSha256,metadataRemoved:true}` for the candidate derivativeProvider dependency. The caller must still perform its independent current employee/media authorization and exact AI recipient/purpose/content/cost approval. This function is not an authorization gate.

No direct changes to runtime or HTTP are included. Candidate adapters still need a derivativeInspector that fully decodes returned PNG pixels. Using this worker's `inspect` meets that interface once the worker has been independently validated and enabled; it launches another isolated job rather than reusing untrusted decoder state. No bytes are cached. An external broker remains a separate deployment integration.

## Trust and execution boundary

The application web process, Supabase/Deno Edge function, browser and ordinary employee process **must not receive a Docker socket or daemon capability**. Node child_process and filesystem APIs do not run in the current Edge deployment. The driver belongs to a dedicated, separately approved, nonroot Linux broker host with its own rootless daemon and narrowly reviewed software/image. A compromise of that broker may control its daemon: rootless is not a substitute for a separate host/service identity and tenant isolation.

The production factory has no injectable platform flag and no Mac fallback. It requires actual Linux, nonroot UID, a local `/run/user/<uid>/docker.sock` socket owned by that UID, and a trusted absolute non-group/world-writable Docker binary. It clears inherited environment, uses a fixed local Unix daemon endpoint (no DOCKER_HOST or context override), and reads actual `docker info` to require rootless, built-in seccomp, cgroup v2 with the systemd cgroup driver, memory/swap/PID and CFS CPU quota/period support. An arbitrary `{isolated:true}` or caller-provided descriptor cannot enable it.

Each request creates a uniquely named container using an existing immutable `sha256:<64 hex>` image ID, `--pull never`, no bind mounts, no request-supplied command/env/path/URL, and fixed Python `-I` entrypoint. Before sending any original bytes it inspects the actual created container and checks image/entrypoint/user, disabled network and container logging (`--log-driver none`, so derivatives are not persisted in daemon stdout logs), read-only root, private IPC/PID/UTS, all capabilities dropped, no-new-privileges, no extra devices/mounts/ports or environment secrets, 1 GiB memory with no additional swap, 1 CPU, 32 PIDs and a 64 MiB nonexecutable private tmpfs. A mismatch is denied and removed. The immutable image itself must have no secrets, volumes, hostile init or writable host integration.

These verified launch properties are necessary, **not sufficient proof of complete security**. Docker info/config is not a physical test that the kernel enforces every cgroup and namespace. The rootless daemon, host kernel, seccomp implementation, immutable image, native libraries, broker identity and monitoring remain part of the trusted computing base. No claim is made about resistance to kernel/container escapes. Actual target-host negative tests below are deployment blockers.

Admission is one in-flight request per instance; busy rejects immediately rather than queueing originals. Operators must enforce a broker-wide concurrency/memory budget across instances. Input is copied and capped at 8 MiB before commands. Metadata output is bounded to 100,000 bytes, stderr is not relayed, and commands have deadlines. The create/inspect/start sequence has a 15-second total deadline, with a separate 5-second cleanup budget. Every attempted create is force-removed by its unique name even if its response was lost. Cleanup failure returns `IMAGE_WORKER_CLEANUP_UNCERTAIN`, withholds results and quarantines that driver instance. Supervisor-level reconciliation must locate and terminate orphan jobs after broker crashes; never automatically retry unknown cleanup as though no work ran. No storage writes or external model calls occur in this worker.

`runPrivateImageWorkerProtocol` and the plan/result validators are low-level seams for synthetic protocol tests, **not** production host verifiers. Runtime code must use the production factory or an independently reviewed broker integration, never substitute mocked execute/inspection results.

## Pixel and metadata contract

`private-image-worker.py` refuses non-Linux/root execution and applies hard RLIMIT_AS 768 MiB, CPU 3 seconds per process, core 0, file size 9 MiB and 32 file descriptors before reading stdin. There is no synthetic-only exception. The outer cgroup limits the aggregate process tree, while the wall-clock supervisor removes the whole container. ImageMagick's configured resource/coder/delegate restrictions are defense in depth, not the OS sandbox.

The fixed deployed binary is `/usr/bin/magick`, version `ImageMagick 7.1.2-17` (same reviewed baseline as the existing inspector). Production packaging must audit the exact binary/libraries and all policy layers; this version check is not a vulnerability review. Input uses explicit PNG/JPEG/WebP coders and a private fixed filename. The Node guard rejects animation/container trailing bytes. `%#` forces full decoded pixel signature calculation, not just magic/header inspection. Only one frame is permitted, maximum 16,384 on an axis and 40 million pixels. Each native subprocess has bounded stdout, rejects any stderr, and is killed on deadline/output overflow. Unsupported images fail without a fallback.

For the derivative, EXIF orientation is applied before stripping. Decode/transform produces raw 8-bit sRGB RGBA pixels with both axes at most **128 pixels**, never upscaling. This conservative first implementation deliberately trades image detail for a provable small output; it may be insufficient for a future product/model and is not approved for technical hair measurements. Python constructs a fresh PNG containing only IHDR/IDAT/IEND with fresh CRCs. No original compressed data, EXIF location, ICC profile, comments, thumbnails or ancillary chunks are copied. The new PNG is below the existing 96 KiB candidate cap. Original bytes remain private and unchanged in storage. A clean derivative can still contain identifiable people and visible text: metadata removal is **not anonymization**, permission to upload privately is **not permission to process externally**.

The protocol binds exact original SHA-256 and derivative SHA-256, dimensions/MIME/frame count and fixed schema. Hashes detect mismatch; they do not by themselves attest trusted decoding. Returns never contain original bytes, EXIF, filenames, URLs, credentials or native diagnostic text.

## Unexecuted deployment checklist and blockers

1. Approve a dedicated Linux broker placement and identity, not the public web/Edge process. Define authenticated bounded IPC with app-only access and fresh authorization, request cancellation, no payload logging, no external egress, global admission, orphan reconciliation and deletion/retention handling. This stage does not open a listener or create credentials/access.
2. Separately approve/build a minimal immutable image from an approved pinned base with Python and reviewed ImageMagick/dependencies. Copy only `private-image-worker.py` into `/opt/design-worker`, fix `/usr/bin/magick`, remove all credentials/unneeded tools/volumes and all environment except standard PATH. Root filesystem owned by root and not writable by UID 65532; `/work` comes only from tmpfs. No Dockerfile/download/install was executed here. Record digest, SBOM, vulnerability review and policy inventory.
3. On the actual rootless Linux/cgroup-v2 host, prove memory/CPU/PID enforcement, no network/DNS, no host filesystem read/write, nonroot/no capabilities/no privilege escalation, no core dumps, cleanup after timeout/crash, global saturation rejection and daemon restart reconciliation. Inspect flags alone is insufficient.
4. Run the complete native corpus inside that image: valid PNG/JPEG/WebP, EXIF orientation/location, truncated data, animation, decompression bombs, excessive dimensions, corrupted CRCs, oversized output and decoder timeout. Validate the new derivative with a separate full decoder and verify only pixel data survives. Test interrupted input and stalled output. None of these proposed-image checks ran in this Mac stage.
5. Review the small derivative's product quality, explicitly select a supported approved model, then wire through the existing exact processing/cost gates. No model choice/paid call is authorized by this implementation.

On macOS the new factory returns `IMAGE_WORKER_HOST_UNSUPPORTED` before process launch. The earlier native inspector's strict RLIMIT_AS refusal remains unchanged. Existing synthetic-whitelist fixtures are still test-only and never become a production escape hatch.

## Web/database startup remains a separate, unconnected boundary

The root application currently exposes a Fetch-style handler factory and receives an injected `acquireClient`; that is not a deployed HTTP server or a configured database driver. GitHub Pages cannot serve `/api/design/*`. The current Deno/Supabase Edge environment cannot execute this Node/native/Docker driver. This change does not add a generic web listener, a connection string, a pool, an Edge proxy, or an authenticated broker API. It does not grant any persistent daemon or database access.

Minimum reviewable startup plan (not a command to run):

1. Web deployment: independently approve the Node service/driver build and its fixed HTTPS public origin. Mount only the existing `/api/design/*` Fetch handler behind an approved bounded HTTPS server/proxy, preserving exact route schemas, employee-token checks, origin rules, no-store responses, streaming limits and safe errors. Keep top-level `enabled:false` until actual acceptance. No public route may invoke arbitrary worker command/image arguments; the worker does not supply an additional public image URL route.
2. Database: provide the existing `acquireClient` from a separately reviewed PostgreSQL driver/pool with bounded waits/concurrency and server-only configuration. Use only required repository statements/roles, no superuser/service-wide write bypass. Schema/RLS, privileges, connections and long-lived credentials require separate approval; injected mock clients are not deployment evidence.
3. Worker broker startup: separately approve a nonroot Linux service account, local rootless daemon access, the reviewed immutable image ID and trusted absolute Docker executable. Its fixed startup configuration begins with `enabled:false`; the only operational image configuration is that reviewed content digest, not an image/tag from requests. Launch worker jobs only after the authenticated application has checked the existing private-media scope. No image secret, DB client, model key or employee token is placed inside containers. A bounded authenticated app-to-broker channel and cancellation/global admission supervisor have not been implemented here and are blockers to multi-host integration.
4. Minimum privilege: web service has only necessary DB/private-storage/model transports and the bounded broker RPC, not Docker socket; broker has no customer database or model credentials, no general outbound network, and only its worker daemon; image containers have no network/host mounts/credentials. Exact host firewall/identity/IPC configuration remains separately reviewed work, not assumed from this document.
5. Rollback: disable root runtime to stop all routes, or disable just the worker/visual-generation dependency for narrower suspension without changing stored original images or previously accepted provenance. Stop broker admission, reconcile and terminate its uniquely identified in-flight containers, verify cleanup before restart. Retain immutable archived provenance and required audit metadata; do not auto-delete customer records or repeat an uncertain model call. Restore only a previously approved immutable service/image revision after forward-compatibility checks, with no forced browser refresh.
6. Acceptance: validate real TLS/origin and employee revocation, bounded bodies/timeouts, DB transaction lifecycle/CAS, private storage publication/recovery, actual Linux isolation negative tests and native corpus, broker authorization/cancellation/orphans and saturation, metadata-strip result provenance, explicit external-processing approval, and full archive/history fidelity. Synthetic tests in this repository alone do not satisfy this checklist.


## Official references checked for this implementation

These describe interfaces and security assumptions, not evidence that our proposed host/image has passed them.

- [Docker rootless resource limits](https://docs.docker.com/engine/security/rootless/tips/#limiting-resources): rootless cgroup limits need cgroup v2 and systemd; controllers available to an unprivileged daemon may be limited. The driver now also rejects missing systemd or CPU quota/period capability reports. Actual delegated controllers and enforced limits still require target-host tests. The same page documents the usual `/run/user/$UID/docker.sock` location; this implementation deliberately supports only that narrower local layout.
- [Docker create command](https://docs.docker.com/reference/cli/docker/container/create/): creation precedes execution, enabling inspection before bytes are sent. Documents pull policy, entrypoint/stdin, capabilities, readonly root, resource, security, network and logging options.
- [Docker Engine API schema](https://docs.docker.com/reference/api/engine/version/v1.51/) and [Moby info JSON fields](https://github.com/moby/moby/blob/master/api/types/system/info.go): basis for Config/HostConfig inspection and `CgroupDriver`, `CpuCfsPeriod`, `CpuCfsQuota` capability names. Matching a documented property name does not validate an actual response from an untested daemon version. Strict serialization checks (such as tmpfs options, security options, image environment, and builtin seccomp label) may reject other safe versions/layouts; this is a deliberate fail-closed compatibility boundary, not a reason to relax checks without target-host review.
- [Docker seccomp](https://docs.docker.com/engine/security/seccomp/): kernel/engine support is required; the default profile applies unless overridden. This driver requires the reported builtin profile and refuses extra container security overrides. The default profile is defense in depth, not a complete sandbox proof.
- [Docker none network](https://docs.docker.com/engine/network/drivers/none/): only loopback remains; it does not mean the container has no networking syscalls or that its broker has no network.
- [Docker logging configuration](https://docs.docker.com/engine/logging/configure/): per-container log driver is visible through `HostConfig.LogConfig.Type`; `none` avoids container logs. It does not disable external broker/proxy/host audit logging, which must separately avoid image payloads.
- [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/): memory/swap and CPU behavior depends on host support; setting memory-swap equal to memory prevents additional container swap. Actual exhaustion and cleanup tests remain mandatory.
- [ImageMagick security policy](https://imagemagick.org/security-policy/): resource, coder, delegate and filter restrictions must be deliberately configured and the active policy inspected; policy ordering matters. This supports the image-build policy inventory and separate sandbox requirements, not an assumption that supplying a policy file overrides every other layer.
- [ImageMagick calculated properties](https://imagemagick.org/escape/): `%#` calculates the image-value signature, `%n` counts images. Together with the non-ping decode and actual raw RGBA output, these underpin the full-pixel processing path; no result from the proposed production image has yet been observed.

The current online ImageMagick documentation is newer than the pinned local 7.1.2-17 baseline. Pinning prevents silent drift but is **not** a claim that this old version is current or security-approved for deployment. Review vulnerabilities and choose/test a new approved immutable baseline before deployment if needed; no software update was performed here.

## Stage 10 local Linux negative-test assessment

Read-only inspection of the existing local Docker daemon reports Linux/cgroup v2, **cgroupfs**, built-in seccomp and cgroup namespaces, but no rootless flag. No approved immutable image containing the specified worker exists locally. This cannot satisfy the production factory's rootless/systemd checks; no host setting was changed and no image was downloaded or built.

`scripts/test-design-linux-isolation-probe.sh` runs only the already installed official `postgres:17` image by its resolved immutable image ID, overriding its entrypoint with a fixed shell probe. It starts no database, reads no host mount and receives no customer bytes or credential. A single uniquely named container has no network, a read-only root, nonroot UID 65532, all capabilities dropped, no-new-privileges, bounded memory/CPU/PIDs and logging disabled. The actual local run verified root writes and protected shadow reads fail, effective capabilities are zero, no-new-privileges is set, the expected cgroup control values are present, and no network route exists. The named container is removed afterward.

These are limited actual negative checks, not proof of CPU/memory/PID enforcement under load, outbound network syscall denial, image decoding, rootless broker security or escape resistance. No stress fork/memory bomb is run on the owner's shared computer. The dedicated host, approved image/native corpus, enforcement under controlled load, authenticated broker/global admission and orphan reconciliation checklist above remains a release blocker. The production factory still refuses this Mac host; test results must never be used to bypass that refusal.
