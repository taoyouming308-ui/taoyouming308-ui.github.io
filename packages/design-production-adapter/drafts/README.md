# Synthetic transaction blueprint, not an installable migration

`visit-binding-transaction.sql` is executable **only in the disposable PostgreSQL 17 fixture** created by `scripts/test-design-binding-postgres.mjs`. It lives outside `supabase/migrations`, is not imported by any production handler or JS transaction executor, and is not a deployment or production-permission change. Do not copy it into a migration directory.

Run the isolated test explicitly with `node scripts/test-design-binding-postgres.mjs`. It requires the already-installed `postgres:17` Docker image. It does not install or pull anything. The runner creates a unique `--rm --pull never --network none` container with no published ports, user-directory mounts or persistent data volume; PostgreSQL data is on that container's tmpfs. Only that newly created container is stopped, and removal is read back. Missing Docker/image access is a failure, not an invitation to fetch, connect to another database, or weaken isolation.

The SQL requires the exact synthetic database name, explicit synthetic connection setting, dedicated fixture marker and PostgreSQL major version. It refuses known public source tables and never creates public objects. Each entry point repeats the fixture check and requires READ COMMITTED. These are accident-prevention guards, not a security sandbox against a database owner who can edit the script or disable triggers.

## Inputs and deliberately missing production integration

The runner creates minimal **source-shaped, wholly fictional** `staff`, `employee_booking_sessions`, `bookings`, `frontdesk_today_customers` and `customer_profiles` tables under `design_binding_fixture`. It creates independent fixture tables for current binding authority, exact immutable approvals and explicit lifecycle decisions. It does not run existing production migrations or reuse real sessions, customer records, passwords, keys or names/phones.

- `apply_binding(session_hash, command, approval_uuid)` supports bind, reassign, revoke and restore. A current scoped manager and an independent exact, unexpired approval of the full command are required, including at deferred commit validation. Commands include request ID, expected latest revision, source visit ID, stable profile ID, store, service date, archive visit key, stylist and lifecycle revision. Revision zero means there is no prior binding. Exact retries return their original result; the request ID cannot be reused for another command, approver reference or operation. An approval cannot be edited or reused for a new command/request. Its request uniqueness supplies fixture single-use behavior; this is not the JS `consumeApproval` implementation, a production approval issuer, or a production approval revocation/consumption ledger.
- Appointment identity is `booking:<positive-integer>`. Frontdesk identity is `frontdesk:<uuid>`, with archive key `manual:<date>:<uuid>`, so separate same-day visits remain separate. The first binding fixes profile/store/date/visit key. Later source reassignment alone denies access; an authorized appended version must match the current source stylist. Reassign must actually change the stylist and may replace a revoked binding. Revoke preserves the old identity and works even when the source row was deleted. Restore requires revoked state, the same saved stylist and fresh source/lifecycle checks. No history is rewritten.
- Lifecycle authorization is a separate trusted decision pinned to the exact source, visit, raw status and lifecycle revision. Numeric booking status `0`, `1`, `3` or `4` is not itself permission. The fixtures do not define production meanings for these status codes. No profile binding is inferred from display name, phone, the requested profile or row order.
- `append_archive(session_hash, command)` rechecks the current session, employee/store, latest binding revision, source assignment, explicit lifecycle decision and profile home store. Its command includes request ID, source visit, profile, expected binding revision, exact expected latest archive UUID (or null) and an **opaque synthetic snapshot**. It appends an immutable archive/version receipt atomically with exact CAS and previous-version linkage. A replay returns its original applied version, not necessarily the current head, and never bypasses current authorization.

The archive fixture models the concurrency/receipt/parent-linkage parts of the existing legacy `customer_design_versions` / `append_customer_design_version` contract. **It does not implement or replay the full legacy document validator, asset ownership checks, photo tables, storage ACLs, production RPC output shape, or a lossless mapping for the new UI.** The synthetic snapshot is not an accepted production payload. The SQL does not implement the JS `transaction(callback)` contract or its adapter response validation. Existing legacy name/phone consistency checks are not promoted to binding authority. A reviewed production implementation must compose all existing validators and scope checks inside the same real transaction and preserve them.

## Lock order and what the proof establishes

For one mutation, the SQL obtains:

1. A transaction-scoped request advisory lock, with a domain-separated request key.
2. Shared locks on the authenticating employee session and current staff row; for binding changes, current manager authority and exact approval rows as well.
3. A transaction-scoped advisory lock for the exact source/visit, including when no binding exists yet. This serializes first bindings, later binding changes and archive head checks for that visit.
4. Shared row locks on the source assignment, exact lifecycle decision, stable profile and target stylist. Binding history rows are immutable. Binding revoke deliberately skips the source/profile checks so deletion cannot prevent revocation.
5. The CAS/read/append and immutable receipt, with all prior locks retained until transaction completion.

Binding and archive constraint triggers are DEFERRABLE INITIALLY DEFERRED. Binding validation rechecks the authorizing manager session, staff and current binding authority, plus source/lifecycle/target staff for active changes; revoke stays source-independent. Archive validation catches same-transaction binding/session/staff/assignment revocation and a session that expires while the transaction remains open. The internal session hash is retained only for deferred checks and is not returned by the functions. Shared row locks conflict with ordinary UPDATE/DELETE, not just fixture API calls. The per-visit advisory lock serializes binding-version appends even though old rows never change.

“Cannot commit after revocation” means transaction serialization: if revocation wins its conflicting lock and commits first, append waits, reads the committed change and fails; if append holds the authorization locks first, revocation cannot commit until append finishes. A successful SQL function return inside an open transaction is not commit evidence. Wall-clock expiry is checked at deferred validation, not a claim about a physically atomic clock check at the storage engine's final commit instruction.

These are conservative locks, not a reviewed production lock protocol. All future writers and legacy RPC composition must follow a compatible order. For example, a writer that holds a source/staff row and then requests the visit/request advisory lock can deadlock with an append that holds the advisory lock and waits for that row. Multiple operations or visits in one transaction need an explicit sorted lock plan. PostgreSQL aborts a deadlock victim; the server must distinguish a confirmed rollback from an uncertain commit and must not blindly issue another request ID. Current tests prove authorization, rollback and observed contention for the documented paths, not absence of deadlocks with every existing production writer. Request hash collisions only over-serialize unrelated work and are not treated as identity equality; exact canonical JSON is compared.

## Verification and remaining gates

The runner uses independent `docker exec ... psql` connections. It observes `pg_stat_activity.wait_event_type='Lock'` and nonempty `pg_blocking_pids` before releasing blockers. JavaScript timers only bound readiness checks; no JS mutex stands in for a database transaction. Tests cover independent approvals/lifecycle, fixed identity, source deletion/reassignment, restore, same-day frontdesk separation, append-only old rows, concurrent binding/archive CAS, concurrent same-request replay, changed-payload conflicts, atomic rollback, revocation-first and append-first lock ordering, deferred same-transaction revocation and actual wall-clock expiry. An isolated pass is not real-user acceptance or production readiness.

Still required before any production enablement: a reviewed authoritative enrollment/lifecycle/revocation policy; stable-ID historical migration decisions; compatibility with every source/session/staff writer and legacy lock domain; non-owner roles, scoped invoker permissions/RLS and direct-insert protection; production approval storage/verifier and identity boundary; canonical input/output validation; full legacy snapshot/asset checks or a separately approved lossless schema; observed production schema compatibility and authorized integration/deployment acceptance. Fixture invoker functions and fixture schema revokes are not a production privilege design. No production grants, credentials, handler wiring or deployment are supplied here.
