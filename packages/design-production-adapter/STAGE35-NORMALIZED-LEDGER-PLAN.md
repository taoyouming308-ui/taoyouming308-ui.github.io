# Stage35 strict normalized ledger integration (isolated acceptance complete; production closed)

Default closed, isolated synthetic qualification only. No production migrations/grants, real keys/customer data, paid provider calls, hosted transforms, image downloads or public listener.

## Integration ownership and boundaries

- New provider intent v6 binds the exact Stage34 strict input, actual prepared body hash, current immutable employee/key revision, workflow head and separate processing/cost receipts. Reuse the original request/attempt ledger; no alternate attempt namespace.
- The canonical proof remains `synthetic_fixture_only`. The new model response is explicitly a mock response; it cannot prove hairstyle quality or qualify arbitrary photographs. Old preview-v3 remains non-adoptable.
- New candidate-v4/history-v3/full-v5 must preserve synthetic origin, unconfirmed observations, subsequent explicit employee confirmation and actual execution as different facts. Historical formats and original authors stay unchanged.
- Final dispatch claim must recheck the complete verified task/report/processing/object ancestry, employee/service relationship, workflow, personal key and processing/cost approval. Unknown acknowledgement never authorizes another send.
- Formal private storage adapter is server-only and injected, disabled by default. Unsupported atomic create-only or exact-version reads fail closed; a path read, ETag or matching digest does not by itself prove immutable storage.
- A safe owner demonstration may use a standalone local artifact with synthetic snapshots, explicitly not a live backend. Do not expose a new network port. Mobile reachability is not assumed.

## Reviewed limitations

- v6 is currently **single before-view, synthetic mock model**. It is not a replacement for the existing multi-angle comparison pipeline. The strict input still describes the fixed 80x120 reference lineage, not ordinary salon photographs.
- Existing v2 completion-synthesis generation from an already upgraded v5 workflow must stay closed unless its provider context first validates the full v3 history and then projects only original v1/v2 comparison ancestors. Pure mixed-history replay supports that projection; it does not by itself wire the old live provider context.
- The new storage adapter has no configured vendor driver. Its backend capability declaration is a trusted deployment prerequisite, not a cloud immutability certificate.
- Unknown send/commit is query-only. The dispatch instance retains admission until late dependencies settle; a never-settling uncertainty cleanup can leave the instance unavailable. It does not retry or expose keys to the user. JavaScript strings cannot be reliably erased; bounded owned byte buffers are wiped.
- The standalone demonstration has no network or persistent storage and is not the live App. File access on a Mac does not establish phone access; mobile-width layout acceptance is not iPhone attachment/browser execution acceptance.
- Original intermittent PostgreSQL failure root cause, long-history performance qualification, actual hosted quota/Spend Cap, arbitrary-photo decoder qualification and production deployment remain separate gates. No current test result resolves them by implication.
