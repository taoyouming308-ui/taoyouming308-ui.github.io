# Stage40: original upload to explicit application-image workflow

Status: locally implemented and synthetically accepted; production remains closed. Baseline b7140e92/v689 clean; current upstream,
startup gates, daily backup and private recovery bundle verified. No production
changes, real photos/keys, paid processing, hosted transform or new image downloads.

## Agreed minimal chain

Original homepage photo panel → private source manifest-v1 with immutable stage/
angle/request binding → independent existing processing approval and once claim →
fixed synthetic source directly normalized to canonical PNG → canonical manifest-v2
→ existing independent task/verifier roles with explicit new task/report/input
versions → shared personal-key/cost/request ledger provider-v7 → candidate-v5,
history-v4 and original prepared/full archive-v6. Do not create a parallel archive,
payment ledger or processing permission system.

There is no hosted-parent object in this direct lane. The real producer matches the
fixed source bytes, then creates PNG directly from that source; independent PNG
inspection compares with a reference generated from that source, not with pixels
before lossy JPEG/WebP encoding. Old parent/native-version paths and stored hashes
remain unchanged. New outputs never fabricate a native objectVersion/immutable
flag. New application-derived writes require fresh existing processing claim and
storage approval; Stage39 source-only entries stay source-only.

Upload belongs to a freshly authorized visit/identity, not a frozen conversation
head. Stage/angle/media/content/request bind atomically before publication and cannot
be relabeled. Model requests later bind the actual current workflow head. Browser
receives only minimal explicit DTOs; storage success is not decode/model permission.
Unknown upload uses original-ID status and explicit GET-only object reconciliation,
never automatic repeat PUT. All new activation is server-configured and default off.

## Scope and rollout limits

Acceptance uses isolated real PostgreSQL, fixed pinned local worker media, mock
object HTTP/model response and full original homepage. It is not arbitrary customer
image qualification or production storage permission proof. Independent backup/
restore, live least privilege, costs/data authorization and cross-epoch historical
regrant remain gates before actual use. No real personal API key is needed now.

## Actual implementation boundary

The new application upload accepts before/after JPEG or WebP with explicit angle,
but this stage's independent direct preparation and candidate-v5 model path is
**before-analysis only**, with pinned synthetic input. The old comparison/synthesis
lanes are not relabelled or silently converted. This is not completion of arbitrary
six-photo application-manifest analysis. The UI hides the old manually entered
normalized-task panel in application mode and carries the verified task selector
internally from an explicit prepare action into a separate model action.

Mixed old and new historical records remain readable; native edits/full archive
preserve new v6 records. After conversion to v6, adding an old managed/view/normalized
candidate is explicitly closed, both in pure code and fixed SQL, rather than silently
downgrading the record. Historical authors and original stored records are unchanged.

Prepare status never repeats processing, object writes, task issuance or verification.
Model status can publish an already-completed candidate to its original durable
candidate repository, but never repeats the external model send. Unknown responses
retain the original request identifier; no permission TTL is extended on retry.

The top-level server composition has separate processing, authorizer and verifier
connections. No processing, content-storage or model-fee permission issuer is
exposed by the HTTP runtime. Synthetic integration fixtures may pre-authorize their
exact known objects and requests; this is not a production approval user journey.

## Pre-production gates, not bypassed by this implementation

1. This code may run only with the explicit synthetic feature flag. Arbitrary real
   JPEG/WebP/HEIC decoding, full-resolution composition/crop/colour/orientation and
   metadata-removal assurance have not been established by the pinned reference.
2. The existing Supabase bucket can be used only after the exact temporary synthetic
   test destination, uploader privileges, spend cap/usage and any charge are checked
   and authorized. No live object was uploaded by this stage. An application-level
   immutable mapping is not vendor object lock or an independent photo backup.
3. Production source/derived grants, short-lived read grants, processing approvals,
   independent verifier/authorizer deployment and model cost approval require a
   reviewed deployment and authorization workflow. The local fixture's explicit
   issuer is not a missing-permission fallback in the product.
4. Actual personal keys must use a secure entry surface; no chat secret, real key,
   external customer photo or paid model call is needed for this synthetic trial.
5. Before real service: test backup and restore (photo objects as well as database),
   finish authoritative identity rollout and historical cross-epoch regrant,
   diagnose the previously observed intermittent PG failure and repeat long-history
   performance under the real deployment. Passing this small fixture does not
   establish those properties.
