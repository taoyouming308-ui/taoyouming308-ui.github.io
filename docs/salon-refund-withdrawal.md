# 退款申请人撤回 · 独立开发批次

状态：仅 `feature/meiguanjia-parity-v1`，本机合成 PostgreSQL / 假身份 / 浏览器测试；没有部署、真实退款、商品返库或整合既有三个 App。

## 规则

- 申请人只能撤回本人、仍为 `submitted`（待审批）的退款申请；审批人和其他员工不能代撤。
- 审批、拒绝、执行后均不可撤回。撤回与审批争用同一申请行锁；先成功的一方确定终态，另一方读取状态后失败。
- 撤回记录单独保存员工、时间和原因，追加审计；原申请保留，状态变为 `cancelled`，因此解除退款额度占用。
- 撤回不创建退款支付、会员流水、库存流水、业绩冲减或订单状态变更。撤回不是退款成功。
- 页面提交携带冻结的申请详情快照、完整请求指纹及幂等键；成功须回读状态/操作者/原因。遇到响应丢失，可在刷新后按原请求号只读核对，不创建第二次撤回。

## 权限与数据

请求需当前员工具备本店 `orders/refund_request`、`orders/refund_read` 与 `orders/read`；服务端再次校验申请创建人、门店范围、待审批状态和快照。RPC 使用 `SECURITY INVOKER`、空 `search_path`，撤销 `PUBLIC`、`anon`、`authenticated` 执行权限，仅授权 `service_role` 通过受控 API 调用。申请原因和撤回原因只写必要业务记录及审计，不进入请求日志正文。

迁移由 Supabase CLI 生成：`20260924040742_salon_refund_request_withdrawal.sql`。迁移未应用至本地默认 Supabase 或任何远端，仅由本机隔离 PostgreSQL 15 按完整迁移序列加载。

## 验收结果

- 专项 PostgreSQL / 手机浏览器测试通过：本人撤回、非本人阻止、审批后阻止、快照变化阻止、幂等同键、丢响应后刷新只读恢复、接口回读核对。
- 撤回前后核对：无反向支付、会员退款流水、商品返库流水、负向业绩/提成；订单退款金额不因撤回改变。
- 全 Salon `.mjs` 模型/API/权限/重放测试通过；退款全额申请、部分申请、审批、现金收银页面/数据库回归通过。
- 尚未完成：商品实物验收及分项可返库数量、实际支付渠道退款回执、会员与组合支付退款、正式 Supabase Auth/Edge/Advisor 验收。实际退款执行入口仍保持未接入页面。
