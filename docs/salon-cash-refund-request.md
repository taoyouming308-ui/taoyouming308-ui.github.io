# 现金全额退款申请

后续更新：首次单笔现金部分退款申请已接入，见 [部分退款边界](salon-partial-cash-refund.md)。已退过订单、多次在途申请、实际退款及返库仍未开放；本文其余内容记录本批原范围。

状态：独立开发、本机合成测试。不是生产退款入口，不合并原三个 App。

## 本批流程

本店订单列表取得内部编号 → 输入原单编号 → 读取原单与唯一现金支付及完整项目分配 → 填写原因 → 人工确认 → 创建待审批申请 → 回读详情 → 其他员工审批。

申请成功不是退款成功，审批通过也不是退款成功。本批不执行退款、不退会员、不返库，不修改支付、订单、库存、会员或业绩账。

## 支持范围与输入

- 仅已支付、正应收、从未退款、唯一已确认现金支付、无冲正、无会员账户/次数的订单。
- 原现金支付必须等于应收；全部原单明细金额为正且合计一致，最多 100 行。全退按原项目数量、金额和原支付自动分配，不允许人工改金额。
- 已有 submitted/approved/executed 申请时拒绝新建。拒绝/取消的历史申请不代表已退款；仍重新检查订单、支付与明细。
- 不支持部分退、组合/会员/电子支付、零元赠送明细。不能把这些订单转换成现金全退绕过检查。
- 页面输入为本店原单内部编号、原因（必填，最多 500 字）；金额来源只读服务端快照，不使用实收现金含找零。
- 商品明细提示返库需另行核实，暂不提供返库选择或执行按钮。未提交输入不持久化；改编号、刷新、切店、重连、退出及业务提交清除旧核对数据。

## 权限与数据最小化

读取、申请和结果查找均需 orders.read、orders.refund_read、orders.refund_request。服务端认证确定员工、组织、授权门店，客户端不能指定其他申请人；本人禁止审批。

原单读取仅返回组织/门店/订单/支付编号、单号、版本、应收金额及项目名称/类型/数量/金额。不读取顾客身份、手机号、会员账户或余额、外部交易凭证、整店财务数据。基础合成角色不默认增加退款权限；专项测试使用独立授权夹具。

## 事务与恢复

CLI 新建迁移 `20260908060101_salon_cash_refund_request.sql`，只在隔离 PostgreSQL 重放，未部署：

- cash_refund_source → salon_get_cash_refund_source：STABLE 只读，严格支持范围。
- cash_refund_request → salon_request_cash_refund：全参数员工指纹，锁原订单后按支付 ID 锁定支付，锁后重新读取完整快照并比较；任何变化要求重新核对。
- 仅插入申请、原单明细/支付分配、审计与原请求完成记录；审计失败整笔回滚。同键同参数返回原回执；同键改参数拒绝；同单不同键并发只能建一条活动申请。
- API 操作名 cash_refund_request，存储动作复用 refund_request，entity_type 为 cash_full_refund，防与旧通用申请请求混淆。
- 函数 SECURITY INVOKER、空 search_path、只授 service_role；匿名及 authenticated 不可直接执行。遵循 Supabase/Postgres 技能的最小权限、短事务与锁顺序约束。

提交后验证原请求号、申请/订单/支付/申请人/金额，再回读核对完整项目分配和原因，成功才清除待核对清单。回读失败只允许只读核对，不再发送写请求。

丢包可同键同载荷重试；刷新后 request_lookup 仅查当前员工/组织/门店原请求，联结原申请，展示原提交事实及当前状态，不重新申请或退款。sessionStorage 仅保存 operation/requestKey，不保存金额、原因或原单明细。查不到不代表失败；关闭标签页、清空存储或跨设备恢复仍未支持。
