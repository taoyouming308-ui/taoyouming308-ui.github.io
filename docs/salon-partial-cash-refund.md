# 首次现金部分退款申请

独立开发分支、本机合成数据。仅创建申请，不执行退款、会员退回、返库或原三个 App 整合。

## 页面与规则

选择“部分退款（首次申请）” → 读取本店原单 → 勾选项目 → 分别填写数量和金额 → 核对分配 → 填写原因 → 人工确认提交 → 回读申请 → 其他员工审批。

沿用旧部分退款函数的数量/金额分别填写、分别限额规则。不按当前售价重算，不擅自按数量比例分摊折扣，不默认原价退款。预览展示每项数量/金额、合计及唯一原现金支付编号；支付分配自动等于明细合计，不允许填另一笔支付。

- 复用现金原单只读入口：已支付、从未退款、无 submitted/approved/executed 申请、唯一已确认现金支付、正金额明细合计等于应收、最多 100 项。默认合成角色不增加权限。
- 可选择多行，同项目不同订单行以行 ID 区分。数量最多三位小数，金额最多两位，均须大于零且不超过原行值；多余精度、科学计数法、重复/跨单明细拒绝，不静默四舍五入。
- 合计须严格小于原单应收；全额走全退入口。仅首次部分退款；已退过订单的剩余额度、多次在途申请未开放。
- 数量不代表商品已退回或验收合格；数量和金额不必按比例，需人工复核。零数量纯金额补偿、零元赠品、会员/电子/组合支付、实际退款及返库判断仍未实现。
- 数量、金额、勾选变化清除预览；重新读取、换编号/模式/门店、刷新、重连、退出和提交清除旧输入。输入仅内存，未提交内容刷新后不恢复。

## 服务端与恢复

CLI 创建 `20260908064655_salon_partial_cash_refund_request.sql`，仅在隔离 PostgreSQL 重放，未迁移生产。

partial_cash_refund_request → salon_request_partial_cash_refund：需要 orders.read、orders.refund_read、orders.refund_request，服务端决定员工、组织和授权门店。SECURITY INVOKER、空 search_path、仅 service_role 可执行，匿名及 authenticated 无直接执行权。

绑定完整员工请求参数 → 锁原订单 → 按 ID 锁原支付 → 重新读取完整原单快照并比较 → 验证各项及合计 → 同事务生成申请、明细/支付分配、审计、完成回执。异常全部回滚。全退与部分退共享原单锁，不能并发生成两条活动申请；同键同参数返回原回执，改数量/金额/原因/身份则拒绝。

request_lookup 支持 partial_cash_refund_request，按组织/门店/申请人/请求号、cash_partial_refund 类型与具体申请关联，与全退和旧通用申请隔离。回执保存原单/支付/申请人、原支付金额、本次金额及精确项目分配。回读须匹配完整分配，刷新后也不能只比较总金额；当前状态与历史提交分开展示。

sessionStorage 仅保存 operation/requestKey，不保存业务金额、原因或项目载荷。丢包同键重试；成功后回读失败保留清单且只允许只读核对。查询不到不等于失败；关闭标签页、清空存储及跨设备恢复未完成。

不读取顾客隐私、会员余额或整店财务。按 Supabase/Postgres 技能落实最小权限、事务校验与锁顺序；权限依据 [官方函数文档](https://supabase.com/docs/guides/database/functions)。默认本机实例不可用，Advisor 未完成，未改连生产。
