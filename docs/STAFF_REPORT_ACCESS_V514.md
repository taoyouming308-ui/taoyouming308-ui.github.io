# 股东报表接入与发布边界

## 使用

1. 总管理员在 `admin.html` 登录，员工管理 → 编辑／新增员工。
2. 账号角色使用普通员工即可；职位可选择“股东”，但职位不是权限。
3. 在“股东报表权限”勾选允许查看的门店，保存。可以授权一店或多店。
4. 该员工正常登录自由手艺人 App，在工作台菜单打开“股东报表”。
5. 取消所有门店授权会关闭入口并拒绝后续读取；离职同时停用账号、撤销股东授权与会话。

财务继续使用原 `operations.html`，账号、密码、原 Auth、保存／入账入口不变。App 内报表不共用财务会话，不可自动入账。草稿仍标记为待财务处理，不代表正式收入。

## 权限实现

- 业务职位、管理角色和股东门店授权独立；本机 localStorage 的角色或勾选状态不能授权。
- `staff-access-api` 管理员令牌只存哈希，绑定实时 staff 身份、密码、角色、门店，2 小时过期。登录及注册限流；注册只能成为待审核员工。
- `staff_access_manage` 一次事务校验管理范围、写员工／授权、附加审计；分店管理员不能配置股东或提升管理角色。
- `staff_report_grants` 精确绑定 staff 主键与门店 UUID。读取用已有 employee_booking_sessions，不使用姓名匹配推断股东。
- operations-api 先校验员工请求只读操作白名单，再验证员工会话、在职、授予门店；报表及原件使用公司／门店／记录三重筛选。
- staff RLS + 列授权：anon/authenticated 仅 SELECT 非敏感目录字段。密码过滤／SELECT *／INSERT／UPDATE／DELETE 均拒绝。私有会话、授权、审计、RPC 仅 service_role。
- 不修改其他历史 App 表，也不声称全部旧系统均已安全改造。既往公开过的凭证需要管理员按计划轮换；本次不重置真实密码或强制财务退出。

## 发布顺序

1. 真实隔离 PostgreSQL、Edge 和浏览器测试，再跑完整 pre-push。
2. 应用 `20260921021140_staff_report_access.sql`（仅新增结构与服务 RPC）。
3. 部署 staff-access-api、employee-bookings-api、operations-api；三者由函数内鉴权，保持既有自定义会话边界。
4. GitHub main 发布 v514，逐字核验 Pages 的兼容页面／脚本。
5. 再应用 `20260921021346_staff_credentials_private.sql`，实时核验匿名密码查询／写权限被拒。
6. 不为测试创建生产员工、不给真实员工授予权限、不调用生产财务保存／入账。真实管理员选择授权对象后，首次真实账号验收仍由用户完成。

数据库迁移为前向发布；如发现客户端兼容问题，修复受保护接口后以更高版本发布，不恢复匿名密码读取或员工写入。未强制刷新使用中的编辑页；旧管理员页遇权限错误时保留输入并提示刷新后重新登录。
