# 门店预约改期 · 本机验收范围

本批支持门店直接修改已确认顾客预约的开始时间，保留原手艺人、项目和服务时长。不是顾客改期申请/审批功能，不发送通知，不收取改期费，不操作会员、支付或库存。

## 接口与状态

- 员工 API：`booking_reschedule`；后端 RPC：`salon_reschedule_booking`。
- 输入：`bookingRequestId`、`requestKey`、`expectedStartsAt`、`expectedEndsAt`、`expectedVersion`、`newStartsAt`、必填 `reason`。
- 日期必须显式带时区；新开始时间必须在未来。结束时间由服务器按原持续时长计算，客户端不能借改期缩短/延长服务。
- 操作者/组织来自验证后的服务端会话；要求当前店同时有 `customer_portal/manage` 和 `scheduling/write`。
- 只处理申请 confirmed、正式预约 confirmed、原手艺人在本店在职、档期状态和归属一致、无任何关联订单的情况。取消待复核、已到店/结束、订单关联、停用/调店等情况拒绝直接改期，保持原数据。
- 原时间、结束时间和改期版本必须全部匹配。每次改期版本递增，即使时间先改走又改回，旧页面也不能覆盖最新记录。
- 输出：申请/预约 ID、confirmed 状态、新起止时间及 `rescheduleVersion`。

## 原子换档与审计

锁顺序：请求号 → 申请 → 正式预约 → 原手艺人 → 档期。手艺人使用兼容外键 KEY SHARE 的 NO KEY UPDATE 锁，串行处理同手艺人的改期。
直接替换当前占用块的时间范围，使用现有排斥约束检查其他预约/休假，不先独立释放旧档期。这样允许与自己的原时间部分重叠，同时避免同时占用两个档期。
申请、正式预约、占用块、版本、处理原因、审计和请求结果在一个事务中更新；冲突或异常回滚全部改动，原预约保留。
`reschedule` 审计追加原时间、新时间、原/新版本、原手艺人、操作者和原因；不删除历史审计。
同键同参数重试只处理一次，改参数/换操作者/撤权后不能重放原结果。旧页面版本冲突需刷新并人工重新确认，不能自动拿新版本重试覆盖。
