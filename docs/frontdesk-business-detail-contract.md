# 收银明细作为日报共用数据源

2026-09-28：用户将实现方向调整为先补齐收银 App 的员工分配业绩和付款来源，日报按向里造型 2026 年 1 月标准读取同一数据。原有来源快照仍作为核对依据。

## 数据流

美管加只读同步 → 私有营业明细 → 前台经营展示 / 财务日报候选 → 财务确认。

两个 App 共享后端明细和映射版本。日报不抓前台 HTML、不依赖前台浏览器打开，不用前台接待表的手填金额说明代替真实收款。前台按会话门店、财务按既有财务门店权限读取。

## 已实现的共用代码

`scripts/mgj_business_detail.py` 提供纯函数 `normalize_bill` 和 `build_day`：

- 单据：源账单 ID、门店、北京时间营业日、源状态/类型、源入账金额。
- 项目：源项目行 ID、项目编码/名称、原分类编码/名称、数量、金额。
- 付款：原字段及来源配置名称、金额分、是否有源值；储值扣卡、优惠等字段均保留原义，暂不猜成实收。
- 员工：员工源编号、岗位、关联项目行、源分配业绩、现金/卡/其他业绩分量、源项目数及人数。
- 店日：完整源列表 ID 与详细单据集合比较、缺少单据、独立付款汇总和员工汇总；缺单时完整入账合计为 null。

金额统一整数分。未知为 null，负数保留并列复核；多个岗位业绩不相加当门店收入。仅明确完整的项目源空列表可显示项目入账 0，仍不能说明全业务零营业。原始快照与标准化摘要需分别保存；`normalized_sha256` 只说明标准化投影，不冒充原始快照 hash。

`scripts/mgj_employee_identity.py` 修复实际源字段冲突：`empfees.empid` 对应 `empList.empId`；`id/employeeId` 可能是重复占位值，不再把它们与有效 empId 混为同一命名空间。仅 empId 缺失时允许非零 fallback，冲突仍拒绝。

## 向里造型 1 月标准的映射边界

| 日报区域 | 明细来源 | 尚需验证的规则 |
| --- | --- | --- |
| 发型师逐人逐项目 | 员工分配 + 项目编码 | 项目编码对应列、岗位归属、点评/抖音与项目是否交叉 |
| 技师逐人逐项目 | 员工分配 + 项目/次数 | 基础/技术项目分类、按次数或金额的原表口径 |
| 零售/售卡/核销 | 相应业务类型完整列表及明细 | 现有项目消费源不涵盖零售和充值售卡 |
| 支付栏 | 单据 paydetail + 有效期内渠道配置 | 实收/卡金/优惠区分、组合付款、退款、渠道历史变更 |
| 汇总和现金流 | 经验证的分类规则和完整店日 | 与已确认 1 月日报逐格比对；门店收入不叠加岗位业绩 |

公-刷卡、公-支微、私-刷卡、私-支微按用户要求不填写。已有确认值保留。新数据仍先作为待财务复核候选。
