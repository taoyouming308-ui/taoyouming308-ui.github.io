# 现金退款剩余额度与多次申请

状态：独立分支、本机合成数据。没有开放实际退款、商品返库、线上登录或原三个 App 整合。

## 本批流程

部分退款／剩余额度 → 读取原现金订单与历史核对 → 分别查看已执行、在途、可申请的金额和数量 → 填写本次明细 → 核对分配 → 提交 → 回读 → 他人审批。

继续沿用数量和金额分别填写、分别限额，不自动按数量比例退款，不使用当前售价重算。

| 状态 | 金额与数量处理 | 是否表示已退钱 |
| --- | --- | --- |
| submitted / approved | 计入在途占用，减少可申请额度 | 否 |
| executed | 计入已执行，必须有匹配反向支付且与订单累计一致 | 账内执行记录，不替代现场支付凭证 |
| rejected / cancelled | 不占用额度；若仍存在其反向支付则拒绝继续核对 | 否 |

每项可申请数量 = 原数量 − 已执行数量 − 在途数量；可申请金额同理。原现金支付的可申请金额也独立校验，必须等于项目可申请金额合计。数量或金额任一耗尽的行不能再选；不支持零数量纯金额补偿。总金额仍有余而数量耗尽时不能强行补数量退款。

可再次申请并可退完剩余金额；单次部分退款仍须小于原订单总应收。初次整单全退继续走旧全退入口，旧入口的“未退过且无活动申请”限制不放宽。

## 核对数据与异常

新 cash_refund_availability 读取：组织/门店/订单/原支付编号、单号、订单版本、原应收，逐项原数量/金额、已执行/在途/可申请数量与金额，以及占用申请的 ID/状态/金额。无顾客身份、电话、会员账户/余额、外部支付凭证或整店财务。

- 仅单笔原现金支付，允许其下已有匹配退款反向支付，不允许混合、会员、电子支付或无申请的旧冲正。
- 每条活动或已执行申请必须有完整原单项目分配、唯一原现金分配，金额合计一致。
- 每条已执行申请必须有对应已确认现金反向支付；每条反向支付必须属于本店本单的已执行申请、指向唯一原现金支付，并匹配金额。
- 申请已执行合计、反向支付合计、订单 refunded_total 三者必须一致；全部退完时原订单及支付应为 reversed，否则应为 paid/confirmed。
- 累计数量、金额超原行、历史跨店/跨单、缺少分配、反向支付不匹配等情况直接报错，清除旧输入，不显示“估算可退额度”，不自动修复历史。
- 最多 100 原单明细、500 条退款历史；超限整体拒绝，不按截断历史计算。零元赠送仍不支持。

## 事务、权限与恢复

CLI 创建 `20260908070633_salon_cash_refund_availability.sql`，仅在隔离 PostgreSQL 重放，未部署：新增只读 STABLE / INVOKER 函数及原单历史/明细历史索引。按 Supabase/Postgres 技能采用最小权限、空 search_path、service_role-only；API 员工、组织和授权门店来自认证。查询需 orders.read / refund_read / refund_request。参考 [Supabase 函数权限](https://supabase.com/docs/guides/database/functions)。

升级 salon_request_partial_cash_refund，签名和 API 操作名不变。事务按原单 → 支付 ID 加锁后调用新额度读取，比较完整快照，包括分项余额及占用申请状态，再检查本次数量/金额不超过当前可申请值。不同请求同时使用旧快照只能一个成功，失败者须重新读取；不会偷偷刷新快照重发。已有申请/审批/执行使用的父单互斥边界保留，不反向锁旧申请行，避免与“申请 → 原单”的审批锁顺序死锁。

全参数员工指纹、审计回滚、原键重试与 metadata-only sessionStorage 清单不变。旧首次申请页面的未完成快照不能用于新提交；已经完成的原键请求仍先返回历史回执。回读与刷新恢复继续逐项匹配原申请，不因新的其他退款改变历史回执。

函数仅新增申请、分配、审计和请求记录，不写资金、订单、会员、库存或业绩。多次执行历史仅在临时数据库通过既有函数构造合成测试，未向页面开放 execute。
